    Section 1.19 Public key cryptography

    Subsection 1.19.1 Symmetric versus asymmetric cryptosystems

    The examples of cryptosystems we have discussed thus far are what is known as symmetric cryptosystems. In these systems, to encrypt and decrypt messages Alice and Bob both use the same key \(k\text{,}\) and thus this shared key must be known to both Alice and Bob somehow. This fact creates a security issue. How do Alice and Bob share the key \(k\text{?}\) Meeting in person and secretly exchanging a key to use is an option, but of course this has many practical shortcomings, especially when the number of participants in our communication network grows, and keys are frequently changed. Alternatively, they could share the secret key over a communication channel, but now the ever-watchful Eve comes into the picture. It was questions such as these that led Whitfield Diffie and Martin Hellman to propose (in their 1976 paper “New directions in Cryptography”) a fundamentally different type of cryptography, known as an asymmetric or public key cryptography.
    🔗

    Definition 1.19.1. Public key cryptography (PKC).

    A public key (or asymmetric) cryptosystem is a cryptosystem
    \begin{align*} E\colon \mathcal{K}\times \mathcal{P} \amp \rightarrow \mathcal{C} \\ D\colon \mathcal{K}\times \mathcal{C} \amp \rightarrow \mathcal{P} \end{align*}
    for which the keyspace \(\mathcal{K}\) consists of pairs \(k=(k_{\text{priv}},k_{\text{pub}})\text{,}\) called public/private key pairs, and such that for all \(k=(k_{\text{priv}},k_{\text{pub}})\text{,}\) we have
    \begin{align*} E_{k} \amp = E_{k_{\priv}} \amp D_k\amp =D_{k_{\pub}} \end{align*}
    so that encryption is performed using the public key \(k_{\pub}\) and decryption is performed using the private key \(k_{\priv}\text{.}\)
    🔗
    Cryptography that uses public key cryptosystems is called public key cryptography.
    🔗
    🔗
    Let’s leave the formalism of Definition 1.19.1 for a moment, and try and understand the asymmetry of this type of system on the level of Alice and Bob.
    🔗
    When Alice uses a public key cryptosystem with encoding/decoding methods \(E\) and \(D\text{,}\) she chooses a public/private key pair \((k_{\priv}, k_{\pub})\text{,}\) and only makes public the public key component \(k_{\pub}\) (we say she publishes the public key). Bob can then use the public key and encryption method \(E\) to encrypt a plaintext message \(m\) as \(c=E_{k_{\pub}}(m)\) and send \(c\) to Alice. Alice can then use her private key \(k_{\priv}\) to recover \(m\) as \(m=D_{k_{\priv}}(c)\text{.}\) Note that there are two different manners in which this setup is asymmetric.
    • The participants in this system use different keys for encryption and decryption.
      🔗
      🔗
    • This system allows for Bob to communicate with Alice, but not conversely, since Bob does not know the key that allows for decryption. In other words, this is a communication with Alice setup, as opposed to a communication between Alice and Bob setup. If Bob also wants to receive messages he can understand, he creates his own public/private key pair.
      🔗
      🔗
    More generally to create a communication network of \(n\) users, so that each user can encrypt outgoing messages and decrypt incoming messages, you have each user \(A_i\) create their own public/private key pair \((k_{\priv,i}, k_{\pub,i})\text{,}\) publish their public key \(k_{\pub,i}\text{,}\) and keep private their private key \(k_{\priv,i}\text{.}\) That way, any user can send encrypted messages to user \(A_i\) as \(c=E_{k_{\pub,i}}(m)\text{,}\) and this message can be decrypted by user \(A_i\) as \(m=D_{k_{\priv, i}}(c)\text{.}\) Note that this public key system requires the production of only \(n\) keys. Using a symmetric cryptosystem for the network, each of the \(\binom{n}{2}\) communication channels would require a key, and for security reasons these would all need to be distinct (the more people that know a specific key, the less secure your network). Thus the number of keys grows as \(n^2\) for this symmetric design, and only as \(n\) for the public key design.
    🔗
    How do we actually design a secure public key cryptosystem? Diffie and Hellman articulated the problem in terms of the notion of one-way functions with trapdoor features. Let’s go back to the simple Bob-communicating-with-Alice setup. To initiate this communication network, Alice seeks an encryption function \(f\colon \mathcal{P}\rightarrow \mathcal{C}\) that satisfies the following conditions:
    1. Values \(f(m)\) of the function \(f\) can be easily computed with sufficient published information.
      🔗
      🔗
    2. The information alone of how to compute values \(f(m)\) of \(f\) does not allow for In general, it is computationally infeasible to invert \(f\text{,}\) so a ciphertext \(c\) intercepted by Eve cannot be decrypted as \(f^{-1}(c)\text{.}\)
      🔗
      🔗
    3. Although difficult in general to compute \(f^{-1}\text{,}\) with some special additional information
      🔗
      🔗
    proposed the following general approach. We need to find a mathematical function \(f\colon X\to Y\) that is easy to compute, but hard to invert. Such a function is called a one-way function. If we can find such a function, then we can use it to create a public key cryptosystem as follows. Alice chooses a one-way function \(f\colon X\to Y\text{,}\) and publishes the description of this function as her public key. To encrypt a message \(m\in X\text{,}\) Bob computes the ciphertext \(c=f(m)\text{.}\) To decrypt the message, Alice uses her private key, which is the trapdoor information that allows her to efficiently compute an inverse of \(f\text{,}\) to recover \(m\) from \(c\text{.}\) Thus, the security of this system relies on the fact that without the trapdoor information, it is computationally infeasible for Eve to invert the one-way function and recover the plaintext message from the ciphertext.
    🔗
    🔗

    Subsection 1.19.2 Diffie-Hellman key exchange

    Diffie and Hellman did not themselves propose an actual example of a public key cryptosystem, but they did describe the following key exchange that makes use of their one-way and trapdoor function concepts.
    🔗

    Definition 1.19.2. Diffie-Hellman key exchange.

    Alice and Bob wish to share a key over an insecure communication channel. The Diffie-Hellman key exchange accomplishes this as follows.
    1. Public.
      Alice and Bob agree publicly on a prime \(p\) and a primitive root \(g\) of \(\F_p\text{.}\)
      🔗
      🔗
    2. Private.
      Alice chooses a random integer exponent \(a\text{,}\) and Bob chooses a random integer exponent \(b\text{.}\) These exponents are kept private.
      🔗
      🔗
    3. Exchange.
      Alice computes \(A=g^a\in \F_p^*\) and sends this value to Bob; Bob computes \(B=g^b\in \F_p^*\) and sends this value to Alice.
      🔗
      🔗
    4. Shared key.
      Alice uses her private exponent \(a\) to compute \(B^a\in \F_p^*\text{;}\) and Bob uses his private exponent \(b\) to compute \(A^b\in \F_p^*\text{.}\) Since
      \begin{equation*} B^a=(g^b)^a=g^{ab}=(g^a)^b=A^b\text{,} \end{equation*}
      Alice and Bob are now in possession of a shared key
      \begin{equation*} k=g^{ab}\text{.} \end{equation*}
      🔗
      🔗
    🔗
    🔗

    Remark 1.19.3. Integers or congruence classes.

    We have chosen to use the language of \(\F_p\) to express the mathematics behind the Diffie-Hellman key exchange; and we will do the same with the Elgamal and RSA cryptosystems below. As usual, we could just as well have described things solely in terms of integers, in which case we would have to make use of the least positive residue function \(\underline{\phantom{A}}\boldmod p\text{.}\) For example, here is an integer-based summary of the Diffie-Hellman key exchange.
    1. Pick a prime \(p\) and an integer \(n\) that is a primitive root modulo \(p\text{.}\)
      🔗
      🔗
    2. Alice chooses a random integer exponent \(a\text{,}\) computes \(A= n^a\boldmod p\text{,}\) and sends it to Bob; Bob chooses a random integer exponent \(b\text{,}\) computes \(B= n^b\boldmod p\text{,}\) and sends it to Alice.
      🔗
      🔗
    3. Alice and Bob use their private exponents \(a\) and \(b\) to compute the shared key
      \begin{equation*} k= n^{ab}\boldmod p= B^a\boldmod p= A^b\boldmod p\text{.} \end{equation*}
      🔗
      🔗
    As you can see, our notational choice has the advantage of notational brevity. The integer-based description is more common in the literature, however, and implemented versions of these systems use integers, not congruence classes.
    🔗
    🔗

    Remark 1.19.4. Fast modular exponentiation.

    The Diffie-Hellman key exchange, as well as the Elgamal and RSA encryption methods below all rely on modular exponentiation. For these various methods to be efficiently used, this operation needs to be performed reasonably quickly. This is possible thanks to a fast method of modular exponentiation that is based on the binary expansion of the exponent. See the Rosen text for more details (or consult your notes from Math 336-1).
    🔗
    🔗
    Before getting to our computational example Sage example 9, we first point out an obvious potential weakness to the Diffie-Hellman key exchange. Namely, if Eve can intercept the transmissions \(A=g^a\) and \(B=g^b\text{,}\) then since \(g\) is publicly known, she could simply find the exponent \(a\) and then compute \(k=B^a\text{.}\) In number theory terms, Eve here has computed the discrete log (or index) of \(A\) to the base \(g\text{.}\) Whether or not the Diffie-Hellman key exchange is vulnerable to this particular attack depends on how easily this discrete log computation can be performed: i.e., it depends on the difficulty of the discrete log problem.
    🔗

    Definition 1.19.5. Discrete log (or index).

    Let \(n\) be a positive integer, let \(g\in (\Z/n\Z)^*\) be a unit of order \(\ord r=m\text{,}\) and let \(h\in \angvec{g}\text{.}\) The unique integer \(k\in \{0,1,\dots, m-1\}\) such that \(h=g^k\) is called the discrete log (or index) of \(h\) to the base \(g\text{,}\) and is denoted by \(\log_g h\) (or \(\ind_g h\)).
    🔗
    🔗
    Finding discrete logs is important enough to number theory and cryptography that it has earned its own name as a computational problem: the discrete log problem.
    🔗

    Definition 1.19.6. Discrete log problem.

    The discrete log problem for modular unit groups is the general problem described as follows: given a positive integer \(n\text{,}\) unit \(g\in (\Z/n\Z)^*\text{,}\) and element \(h\in \angvec{g}\text{,}\) find the unique integer \(a\in \{0,1,\dots \ord g-1\}\) such that \(h=g^a\) (i.e., compute \(\log_g h\)).
    🔗
    🔗
    Eve’s discrete log attack on the Diffie-Hellman key exchange is just the most obvious one. There may be other attacks, and indeed, cracking a general Diffie-Hellman key exchange may be easier than solving the discrete log problem. Accordingly, we give this computational problem its own name.
    🔗

    Definition 1.19.7. Diffie-Hellman problem.

    The Diffie-Hellman problem is the general problem described as follows: given prime integer \(p\text{,}\) primitive root \(g\in \F_p\text{,}\) and powers \(g^a\) and \(g^b\text{,}\) compute the power \(g^{ab}\text{.}\)
    🔗
    🔗

    Remark 1.19.8. Discrete log and Diffie-Hellman problems.

    1. It is clear that a solution to the discrete log problem could be used to solve the Diffie-Hellman problem. The converse is unknown: that is, it is not known whether a solution to the Diffie-Hellman problem would give rise to a solution to the discrete log problem.
      🔗
      🔗
    2. The discrete log problem for general prime \(p\) is considered to be difficult to solve in general. In particular there is no known algorithm for computing discrete logs modulo \(p\) whose runtime is polynomial in \(\log p\text{.}\)
      🔗
      🔗
    3. The discrete log problem can be solved efficiently if \(p-1\) has small prime factors, thanks to the Pohlig-Hellman algorithm (an application of the CRT). Since \(p-1\) is always even (for large primes), a Diffie-Hellman key exchange protocol should us a prime \(p\) such that \(p-1=2q\text{,}\) where \(q\) is a large prime, or equivalently, \(p=2q+1\text{.}\) Such primes are called safe primes in the cryptographic literature.
      🔗
      🔗
    🔗
    🔗

    Subsection 1.19.3 Encoding to integers

    Below we discuss two public key cryptosystems, Elgamal and RSA. Both systems use as their plaintext and ciphertext spaces a modular ring \(\Z/n\Z\) for some integer \(n\) (or \(\{0,1,\dots, n-1\}\) if you prefer to work with integers). In other words the plaintexts that are encrypted and decrypted are themselves just congruence classes \([a]_n\in \Z/n\Z\text{.}\) This might seem somewhat limiting. What’s the use of communicating integer messages to one another? Isn’t a string of characters a more natural thing to communicate? Indeed, it is, but we can easily encode strings of characters as integers.
    🔗
    For example, the ASCII system assigns to each integer \(m\in \{0,1,\dots, 127\}\) a character. The Sage commands chr() and ord() convert integers in this range to characters, and inversely. The first 32 integers of the ASCII range are reserved for non-printing control characters with string literals like \n (newline) and \t (tab).
    🔗
    The ASCII functions give us a way to encode individual characters as integers lying in \(\{0,1,\dots, 255\}\text{.}\) To encode an entire string of characters \(s=a_0a_1\cdots a_{k}\) as an integer, we can convert each character \(a_i\) to its ASCII integer \(t_i\text{,}\) and then assign to the string \(s\) the integer \(a\) with base-256 expansion \((t_0t_1t_2\cdots t_{k})\text{:}\) i.e., we set
    \begin{align} a \amp = t_0\, 256^{k}+t_1\, 256^{k-1}+\cdots+t_{k-1}256+t_k\text{.}\tag{1.19.1} \end{align}
    🔗
    🔗

    Subsection 1.19.4 Elgamal encryption

    The Elgamal public key cryptosystem was first described in a 1985 paper by Taher Elgamal titled A public key cryptosystem and a signature scheme based on discrete logarithms. Although chronilogically more recent than the RSA cryptosystem, we treat it first for its obvious connection to the Diffie-Hellman key exchange.
    🔗

    Definition 1.19.9. Elgamal encryption.

    Bob wishes to send messages to Alice over an insecure channel. The Elgamal cryptosystem accomplishes this as follows.
    1. Public.
      Alice publishes a large prime \(p\) and a primitive root \(g\) of \(\F_p\text{.}\)
      🔗
      🔗
    2. Private.
      Alice chooses a random integer exponent \(a\text{,}\) and keeps this exponent private.
      🔗
      🔗
    3. Public key.
      Alice computes \(A=g^a\in \F_p^*\) and publishes this value as her public key.
      🔗
      🔗
    4. Encryption.
      To encrypt a message \(m\in \F_p\text{,}\) Bob chooses a random integer \(k\text{,}\) computes the elements \(c_1=g^k\) and \(c_2=m\cdot A^k\) in \(\F_p\) , and sends the ciphertext \((c_1, c_2)\) to Alice.
      🔗
      🔗
    5. Decryption.
      To decrypt the message, Alice uses her private key \(a\) to compute
      \begin{gather*} c_1^{-a}c_2\text{.} \end{gather*}
      To see that this is indeed \(m\text{,}\) note that
      \begin{align*} c_1^{-a}c_2 \amp = (g^k)^{-a}(m\cdot A^k)\\ \amp = m\cdot g^{-ka}g^{ka}\\ \amp = m\text{.} \end{align*}
      🔗
      🔗
    🔗
    🔗

    Sage example 10. Elgamal encryption and decryption.

    Below you find the relevant Sage functions for Elgamal encryption and decryption. We’e included our str2int() and int2str functions discussed in Subsection 1.19.3. Coding-wise, it is slighly more convenient here to work with integers, as opposed to congruence classes. You will notice that we use power_mod(g,k,p) which is a fast modular exponentiation function to compute \(g^k\boldmod p\text{.}\) Encoding-wise, we are using a smaller character set so that our messages encode to integers that are smaller than our prime \(p\text{.}\)
    🔗
    Now we will have Alice set up a public key \((p,g,A)\text{.}\) As with the Diffie-Hellman key exchange, Alice will choose a large safe prime \(p=2q+1\text{,}\) with \(q\) prime.
    🔗
    Now Alice creates the rest of her public key, keeping her integer exponent \(a\) private.
    🔗
    Bob now encodes a message as an integer and encrypts it using the Elgamal public key \((p,g,A)\text{.}\)
    🔗
    And now Alice decrypts the message using her private key \(a\text{,}\) making sure to convert the resulting integer back to a string.
